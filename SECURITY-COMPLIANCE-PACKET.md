## 1. Executive Summary

Carevo is an AI care-routing platform for health insurers and healthcare facilities. The patient-facing product asks focused symptom questions, checks emergency signals first, and routes people toward emergency services, ER, urgent care, primary care, telehealth, or home care. Carevo AuditOS is the enterprise monitoring layer for route safety, consent state, decision traces, audit readiness, and cost operations.

Carevo's core safety design is intentionally not "LLM decides care level." The language model helps extract structured facts and phrase plain-language questions. The final care route is produced by a deterministic TypeScript rules engine with emergency-first safety floors, replayable provenance, and evaluation gates that treat under-triage as release-blocking.

This packet is a readiness document, not a certification report. Carevo should not claim SOC 2, ISO 27001, or HIPAA compliance today. For covered-entity or business-associate production use, Carevo will need signed BAAs where applicable, formal policies, access controls, incident-response procedures, vendor review, and a documented HIPAA Security Rule risk analysis.

## 3. Product and Data Flow

1. **Patient message received**
   - User enters symptom text in the Carevo intake flow.
   - The app does not require name, email, phone number, member ID, address, or medical record number.

2. **Emergency net runs first**
   - A deterministic emergency screen runs before ordinary AI processing.
   - Clear emergency or self-harm language triggers immediate safety guidance before routine routing.

3. **AI extracts structured facts**
   - The model converts patient text into a feature vector such as symptom family, red flags, duration, age band, and other routing-relevant facts.
   - The model does not choose the care level.

4. **Deterministic routing engine decides**
   - Carevo's rules engine applies safety floors and risk modifiers.
   - Rules may raise acuity when risk is detected. They are not trainable or bypassable by user text.

5. **Patient-facing response is phrased**
   - The model can phrase a question or recommendation in plain language.
   - Patient-facing text is constrained to established facts and retrieved evidence.

6. **Optional research sharing**
   - After the assessment, users can choose whether to share the conversation for quality review.
   - Sharing is opt-in. If shared, the user receives a deletion code.

7. **Audit and monitoring**
   - AuditOS displays case route, matched rule, questions asked, safety status, consent status, and operational metrics.

## 5. Security Controls Implemented

| Control | Current implementation |
|---|---|
| HTTPS and transport security | Vercel-managed TLS with HSTS configured in `next.config.mjs`. |
| Security headers | Content Security Policy, frame denial except same-origin embed route, MIME sniffing protection, referrer policy, permissions policy, COOP, DNS prefetch off, and cross-domain policy restrictions. |
| API cache control | API responses are marked `no-store, no-cache, must-revalidate`. |
| Backend-only AI calls | AI provider calls happen through server/API code, not from browser JavaScript. |
| Input validation | API endpoints use bounded schemas, sanitization, and route-specific input checks. |
| Rate limiting | POST endpoints use per-IP limits to reduce abuse and AI-cost drain. |
| Secret handling | `.env.local` is intentionally excluded from git; secrets are expected to live in host environment variables in production. |
| Admin access | Metrics, research logs, and review surfaces require a configured admin key. Missing keys fail closed. |
| Auditability | Decision records are designed to include route inputs, matched rules, software versions, and provenance. |
| Data minimization | No public accounts, no required identifiers, no ad pixels, and no third-party analytics scripts on health pages. |
| User deletion path | Opt-in research shares receive deletion codes that can be honored through admin tooling. |

## 6. AI Safety Controls

| Safety principle | Carevo approach |
|---|---|
| Emergency first | Emergency and self-harm checks run before ordinary routing. |
| Human-readable routing | Recommendations explain the care level and relevant next steps in plain language. |
| Deterministic final routing | The LLM does not choose ER, urgent care, primary care, telehealth, or home care. |
| Safety floors | Clinical rules can raise acuity but cannot lower emergency protections. |
| Vague user handling | The system asks tailored follow-up questions instead of guessing when the initial message is too thin. |
| Evaluation gates | Under-triage and forbidden outputs are treated as release-blocking failures. |
| Recursive Experience Engine | REE reviews weak sessions, generates candidate training rows, and requires safety gates before model changes are considered. |

## 7. HIPAA Readiness

The HHS HIPAA Security Rule requires safeguards for electronic protected health information across administrative, physical, and technical categories. HHS also explains that business associates handling PHI on behalf of covered entities need written agreements that limit use/disclosure and require safeguards.

Carevo's current public demo is positioned as a care-navigation prototype and does not require identifiers. Before deploying with a payer, provider, or health system where PHI is processed, Carevo should complete:

| Requirement | Action before production PHI |
|---|---|
| Business Associate Agreements | Sign BAAs with customers and vendors that create, receive, maintain, or transmit PHI. |
| HIPAA Security Rule risk analysis | Document risks to ePHI confidentiality, integrity, and availability. |
| Access control | Add authenticated accounts, MFA, role-based permissions, session timeout, and access review. |
| Audit controls | Persist tamper-evident logs in production infrastructure with defined retention. |
| Encryption at rest | Use encrypted PostgreSQL or equivalent durable storage for PHI. |
| Incident response | Define owner, severity levels, customer notification process, and breach assessment workflow. |
| Workforce policies | Document access rules, training, onboarding/offboarding, and minimum-necessary handling. |
| Vendor management | Maintain a vendor inventory, DPAs/BAAs, security review notes, and data-flow map. |

## 8. SOC 2 Readiness

SOC 2 is usually the more buyer-friendly enterprise security milestone after early pilots begin. Carevo is not SOC 2 audited today. A realistic path is:

1. **Readiness phase**
   - Control inventory
   - Asset/vendor list
   - Access policy
   - Change-management process
   - Incident-response plan
   - Secure development policy
   - Evidence collection habits

2. **SOC 2 Type I**
   - Auditor reviews design of controls at a point in time.
   - Best first milestone once Carevo has serious enterprise prospects asking for it.

3. **SOC 2 Type II**
   - Auditor reviews operating effectiveness over a period of time.
   - Best after production operations are stable and evidence collection is routine.

The most relevant SOC 2 trust-service categories for Carevo are Security, Confidentiality, Availability, and Privacy. Processing Integrity may become more important as Carevo becomes more deeply integrated into payer or EHR workflows.

## 9. ISO 27001 Readiness

ISO 27001 can matter for later enterprise and international buyers, but it is usually not the first paid compliance step for an early U.S. healthcare startup. Carevo should build the same evidence foundation used for SOC 2 first: asset inventory, access reviews, policies, risk register, vendor management, incident response, change management, and continuous monitoring.

## 12. Partner-Facing Summary

Carevo is building AI-native care-routing infrastructure for healthcare operations. The product is intentionally designed so the model does not independently choose the care level. Emergency checks, deterministic routing floors, structured provenance, consent-aware research sharing, and AuditOS monitoring give insurers and healthcare teams a clear path toward safer, auditable navigation workflows.

For an early pilot, Carevo can be evaluated as a prototype with limited or no real PHI. For production use with covered entities or business associates, Carevo should complete the required contracts, risk analysis, access controls, and evidence collection before processing PHI.
